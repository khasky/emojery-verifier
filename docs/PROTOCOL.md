# Protocol: the Emojery log, byte by byte

This is the byte-level specification of the Emojery transparency log: the leaves, the signed messages they carry, the tiles and checkpoints that publish them, the anchors that pin the checkpoints, and the rules a verifier applies. Everything a second implementation needs is here.

Normative words (MUST, MUST NOT, SHOULD) are used in the RFC 2119 sense. Hex is lowercase. Every example in this file is a test vector, typed from this file rather than generated by code.

## 1. Encodings

| Name | Bytes |
| --- | --- |
| `u8`, `u16`, `u32`, `u64` | unsigned integer of 1, 2, 4 or 8 bytes, big-endian |
| `lp16(s)` | `u16(len) ‖ utf8(s)`; `len` is the byte length of the UTF-8, at most 65535 |
| `lpb16(b)` | `u16(len) ‖ b` for raw bytes |
| `lp32(s)` | `u32(len) ‖ utf8(s)`; used in one place only, the nullifier formula (§4.1) |
| `sha256(x)`, `sha512(x)` | FIPS 180-4 digests of the bytes `x` |
| `base64url` | RFC 4648 §5 alphabet, no padding |
| `base64` | RFC 4648 §4 alphabet, with padding |

`‖` is concatenation. There is no encoding named `lp`: a field is encoded with exactly the function its table names. All strings are UTF-8 and MUST be well-formed; a decoder runs in fatal mode and a leaf with ill-formed UTF-8 is invalid. Nothing normalises strings (no trimming, no Unicode normalisation): the bytes are the value. Decimal numbers in text (sizes, `at`, `N`, `M`) have no leading zeros, `0` excepted.

**Ed25519** is RFC 8032 Ed25519 verified cofactorless, as WebCrypto does: `S` must be below the group order `L`, and `R` and the public key must be canonical encodings. Every verifier implements exactly this; a signature one implementation accepts and another refuses would split verdicts.

Which function encodes which field:

| Field | Function | Where |
| --- | --- | --- |
| `site`, `target_id`, `reaction`, `prev_reaction` | `lp16` | REACT leaf, REACT signature |
| `iss`, `aud` | `lp16` | ENROLL leaf |
| `iss`, `sub`, `aud` | `lp32` | nullifier formula only |
| `reason_code`, `reason` | `lp16` | REVOKE, RETIRE |
| `log_origin`, `log_name`, domain tags | `lp16` | every signed message |
| `nullifier`, `modulus_hash`, `account_pubkey`, `proof_hash`, `case_id`, `sig` | `lpb16` | leaves |
| `enroll_seq` | `u64` | REACT, REVOKE, RETIRE |
| `counter`, `ban_until` | `u32` | REACT, REVOKE |
| `exp` | `u64` | session refresh signature |

## 2. Names

A log has a **name** (`log_name`) and a current **origin** (`log_origin`):

| Log | `log_name` | First origin |
| --- | --- | --- |
| production | `log.emojery.app` | `log.emojery.app/g0` |
| staging | `log-staging.emojery.app` | `log-staging.emojery.app/g0` |

The origin is `<log_name>/g<k>`, where `k` is the **generation**. A log starts at `g0`; only a rewind record (§9) opens `g<k+1>`. The origin is the first line of every checkpoint and is part of every REACT signature; the name, without the generation, names the log's signing key.

## 3. Leaves

Every leaf starts with two bytes:

| Byte | Meaning |
| --- | --- |
| `version` | the schema version of this leaf's op; `0x02` for all four ops below |
| `op` | `0x01` REACT, `0x02` REVOKE, `0x03` ENROLL, `0x04` RETIRE |

The version is per op, not per format: a new ENROLL schema becomes `0x03` for ENROLL alone, and the other ops keep `0x02`. `0x00` and `0x01` are never versions, which keeps `enroll_hash` (a hash of raw leaf bytes) apart from the RFC 6962 hashes, whose inputs start with `0x00` and `0x01`. A record whose first byte is `0xff` is reserved and is invalid in this version. Unknown ops and versions are invalid.

A leaf is exactly its fields: a decoder rejects a leaf whose length prefixes run past the end or that has bytes left over. Leaves carry no time; a leaf's position in the tree is its sequence number, `seq`, counted from 0.

### 3.1 REACT (op 1): set, change or clear a reaction

```text
u8    version         02
u8    op              01
u64   enroll_seq      the seq of the ENROLL leaf of the signing device key
lp16  site            1-32 bytes [a-z0-9]
lp16  target_id       1-256 bytes
lp16  reaction        0 bytes (clear) or 1-64 bytes
lp16  prev_reaction   0 bytes (the pair had no reaction) or 1-64 bytes
u32   counter         per pair, increasing
lpb16 sig             64 bytes, Ed25519
```

Example, 112 bytes — device key ENROLL at seq 1 puts 👍 on GitHub repository `khasky/emojery` for the first time:

```text
02 01
0000000000000001
0006 676974687562
000e 6b6861736b792f656d6f6a657279
0004 f09f918d
0000
00000001
0040 <64 signature bytes>
```

**REACT signature.** Ed25519 by the device key over:

```text
lp16("emojery-react-v2") ‖ lp16(log_origin) ‖ enroll_hash ‖ lp16(site) ‖ lp16(target_id) ‖ lp16(reaction) ‖ lp16(prev_reaction) ‖ u32(counter)
```

- `log_origin` is the origin of the generation in which the leaf is sealed, with the generation: `log.emojery.app/g0`. A client signs only for the first origin of its log or for the `origin` of a rewind record (§9) it has itself verified; it never takes a new origin from an API answer alone.
- `enroll_hash` is 32 raw bytes, `sha256` of the full ENROLL leaf the REACT points at (§3.3). It is not in the REACT leaf; a verifier computes it from the ENROLL at `enroll_seq`.
- The tag names the leaf version: a REACT `0x03` will carry `emojery-react-v3`, so a signature for one version never fits the bytes of another.

The kind of change follows from the two reactions: `prev_reaction` empty and `reaction` set is an add, both set is a change, `reaction` empty is a removal.

### 3.2 REVOKE (op 2): the operator withdraws every vote of an account

```text
u8    version       02
u8    op            02
u64   enroll_seq    an earlier ENROLL of the account
lp16  reason_code   1-32 bytes [a-z_]
lpb16 case_id       16 bytes, the operator's decision id
u32   ban_until     day number (days since 1970-01-01 UTC) from whose start the ban ends; ffffffff = no end
```

Example, 52 bytes — revoke the account behind ENROLL 2 for `coordinated_voting`, banned without an end date:

```text
02 02
0000000000000002
0012 636f6f7264696e617465645f766f74696e67
0010 00112233445566778899aabbccddeeff
ffffffff
```

`ban_until` records the ban that applied when the revocation was written; it does not date the event. One REVOKE covers every pair of the account.

### 3.3 ENROLL (op 3): a device key, proven to belong to a real provider account

```text
u8    version         02
u8    op              03
lpb16 nullifier       32 bytes (§4.1)
lp16  iss             the provider's issuer, one fixed form per provider
lp16  aud             the Emojery client id at that provider
lpb16 modulus_hash    32 bytes: sha256 of the RSA modulus n of the provider key that signed the id_token, big-endian, no leading zero bytes
lpb16 account_pubkey  32 bytes, the Ed25519 device key
lpb16 proof_hash      32 bytes: sha256 of the zero-knowledge proof
```

`enroll_hash = sha256(ENROLL leaf bytes)`, from `version` to the end of `proof_hash`, with no `0x00` prefix. The proof itself is the object `g<k>/proofs/<seq>` (§6); the leaf commits to it through `proof_hash`.

An ENROLL is 142 bytes plus `iss` and `aud`: 241 from Google (`iss` 27 bytes, `aud` 72), 167 plus the client id from Apple (`iss` 25 bytes).

`account_pubkey` MUST NOT be a point of small order (one of the eight torsion points, in any encoding): such a key would let one signature verify under different implementations differently.

### 3.4 RETIRE (op 4): an account was deleted

```text
u8    version     02
u8    op          04
u64   enroll_seq  an earlier ENROLL of the account
lpb16 nullifier   32 bytes, equal to the nullifier of that ENROLL
lp16  reason      "self", "request" or "legal"
lpb16 sig         64 bytes for "self", empty otherwise
lpb16 case_id     empty for "self", 16 bytes otherwise
```

- `self`: the owner deleted the account. `sig` is Ed25519 by the device key of the ENROLL at `enroll_seq` over `lp16("emojery-retire-v1") ‖ lp16(log_name) ‖ enroll_hash`. The signature names the log, not the generation: `enroll_hash` already binds it to one registration. 118 bytes.
- `request`: the operator deleted it at the owner's request; `legal`: under a legal obligation. `sig` is empty and `case_id` names the decision. 73 and 71 bytes.

### 3.5 Limits a verifier enforces

| Field | Rule |
| --- | --- |
| `site` | 1-32 bytes, `[a-z0-9]` |
| `target_id` | 1-256 bytes, well-formed UTF-8 |
| `reaction`, `prev_reaction` | 0 or 1-64 bytes, well-formed UTF-8 |
| `counter` | any `u32`, greater than the pair's previous counter |
| `reason_code` | 1-32 bytes `[a-z_]` |
| `reason` | exactly `self`, `request` or `legal` |
| `case_id` | 16 bytes; empty only on RETIRE `self` |
| `sig`, `nullifier`, `account_pubkey`, `modulus_hash`, `proof_hash` | 64, 32, 32, 32, 32 bytes |
| `iss`, `aud` | a pair listed for this log (§11) |

These are shape rules. Which sites exist, how a site's `target_id` is spelled and which reactions are in the palette are the publisher's rules (`@emojery/shared/sites`, `@emojery/shared/palette`): they change without a verifier release, and a verifier does not apply them to published leaves. A leaf the publisher accepts always passes these rules.

## 4. Identity formulas

These are fixed by the zero-knowledge circuit and are raw tags, not `lp16` tags.

### 4.1 Nullifier

```text
nullifier = sha256("emojery-nullifier-v1" ‖ lp32(iss) ‖ lp32(sub) ‖ lp32(aud) ‖ salt)
```

`sub` is the provider's user id and never leaves the circuit; `salt` is the operator's 32-byte secret, committed to by `salt_commitment = sha256(salt)` (§11). One provider account always yields one nullifier in one log.

### 4.2 Nonce

```text
nonce = hex(sha256("emojery-nonce-v1" ‖ account_pubkey ‖ nonce_salt))
```

64 lowercase hex characters; `nonce_salt` is 32 random bytes chosen by the client. The provider signs the `nonce` claim inside the id_token, which ties the token to the device key.

### 4.3 Proof public inputs

The proof is an UltraHonk proof with verifier target `evm` (Keccak transcript, zero-knowledge). Its public inputs, one field element each, in this order:

```text
modulus_limbs[18]  redc_limbs[18]  iss.storage[96] iss.len  aud.storage[128] aud.len  nullifier[32]  salt_commitment[32]  account_pubkey[32]
```

358 inputs. `modulus_limbs` are the 2048-bit modulus split into 18 limbs of 120 bits, least significant first; `redc_limbs` the same split of `floor(2^4102 / n)`; strings are zero-padded byte arrays followed by their length (`iss` at most 96 bytes, `aud` at most 128); the 32-byte values are one input per byte. The verifier builds all 358 from the leaf, the provider key named by `modulus_hash` and the pinned `salt_commitment`, and recomputes `redc` itself. The provider key MUST be RSA with exactly 2048 bits and `e = 65537`. The verification key is selected by the ENROLL version (§11).

The proof object `g<k>/proofs/<seq>` is the raw proof as the prover writes it, without public inputs; `proof_hash` is the sha256 of exactly those bytes.

## 5. Hashes and the tree

```text
leaf_hash = sha256(0x00 ‖ leaf bytes)
node_hash = sha256(0x01 ‖ left ‖ right)
```

The tree is the RFC 6962 Merkle tree over `leaf_hash` in `seq` order; inclusion and consistency proofs are RFC 6962 proofs. The root of the empty tree is `sha256("")`.

## 6. Published files

All files of a log live under one host (`https://log.emojery.app/` for production):

```text
index.json                         signed records (§9)
g<k>/checkpoint                    the latest checkpoint of generation k (§7)
g<k>/tile/<L>/<N>[.p/<W>]          hash tiles
g<k>/tile/entries/<N>[.p/<W>]      entry bundles
g<k>/proofs/<seq>                  the proof of the ENROLL leaf at seq, raw bytes
g<k>/jwks/<provider>/<hex sha256(n)>.json   the provider key an ENROLL names (§10)
g<k>/anchors/<size>.json           the anchor of the checkpoint of that size (§8)
g<k>/anchors/latest.json           the newest anchor
```

Tiles follow C2SP tlog-tiles: width 256; a hash tile of level `L` holds the hashes of tree level `8·L` (level 0: the leaf hashes); a tile of fewer than 256 entries exists only at the right edge and carries `.p/<W>` (`W` 1-255). `<N>` is written in groups of three digits, every group but the last prefixed with `x`: tile 1234067 is `x001/x234/067`.

An entry bundle `tile/entries/<N>` holds leaves `256·N` to `256·N + 255`, each as `u16(length) ‖ leaf bytes`. An object's **last leaf** is the last leaf under it: `256·N + W − 1` for a bundle of width `W`, `(256·N + W)·256^L − 1` for a hash tile of level `L`.

Full tiles and bundles are written once and never change. Partial objects stay until the full object of the same level and index is written; then the publisher deletes them. A reader asks for the partial of the width its tree size implies and, on `404`, for the full object, whose first `W` entries are that partial's. The partials at the size where a generation closed are never deleted.

After a rewind (§9), objects that lie wholly below the boundary `N` of the closed generation stay under its prefix: an object whose last leaf is below `N` is read under `g<k>`, any other under `g<k+1>`. In general a generation keeps the leaves below its start (`N` of the record that opened it; 0 for `g0`) from the generation before it and seals every leaf from its start on, so the generation that **sealed** a position is found by walking back from the current one to the first whose start is at most that position. An object lives under the prefix of the generation that sealed its last leaf, and a REACT is signed for the origin of the generation that sealed it (§3.1).

## 7. Checkpoint

A C2SP signed note (`c2sp.org/signed-note`) whose text is a C2SP checkpoint (`c2sp.org/tlog-checkpoint`):

```text
log.emojery.app/g0
1048576
<root, base64>

— log.emojery.app <base64(key_id ‖ signature)>
```

- Line 1 is the origin, line 2 the tree size in decimal, line 3 the root. Further lines before the blank line are extensions; a verifier accepts and ignores them.
- The signature is Ed25519 by the log key over the text: every line up to and including the newline before the blank line.
- The key name is `log_name`, without the generation, so a rewind does not change the key. `key_id = sha256(log_name ‖ 0x0a ‖ 0x01 ‖ public key)[0:4]`.
- Signature lines under other key names are ignored: third-party cosignatures can be added without a format change.

## 8. Anchor

Every 30 minutes, when the log has grown, the checkpoint is anchored in Sigstore Rekor v2. The anchor file:

```json
{
  "kind": "rekor-v2",
  "note": "log.emojery.app/g0\n1048576\n<root>\n\n— log.emojery.app <signature>\n",
  "anchoredAt": 1789944536,
  "prev": 1047552,
  "rekor": {
    "origin": "log2026-1.rekor.sigstore.dev",
    "logIndex": 2903793144,
    "anchorSig": "<base64>",
    "entry": "<base64 canonical entry body>",
    "inclusionProof": {"logIndex": "<n>", "treeSize": "<n>", "rootHash": "<base64>", "hashes": ["<base64>"], "checkpoint": "<the shard's signed checkpoint>"}
  }
}
```

- `kind` selects the check. A verifier that does not know a kind treats the anchor as missing (`WAIT`), never as a failure.
- `note` is the full signed checkpoint, signature lines included. It MUST verify as a checkpoint of this log.
- `anchorSig` is Ed25519ph (RFC 8032, empty context) by the log key over the UTF-8 bytes of `note`. The Rekor entry is a `hashedrekord` v0.0.2 whose digest is `sha512(note)`, whose signature is `anchorSig` and whose key is the log's public key with key details `PKIX_ED25519_PH`. `entry` is that canonical body, and the shard's leaf is `sha256(0x00 ‖ entry)`.
- `inclusionProof` proves `entry` in the shard under `checkpoint`, a signed note of the shard checked with the shard key pinned in the verifier (§11); `rekor.logIndex` MUST equal `inclusionProof.logIndex`. An anchor in a shard the verifier does not pin cannot be checked and counts as no anchor.
- `anchoredAt` is the publisher's clock, in Unix seconds, when the shard answered. Rekor v2 entries carry no time of their own. The value is the operator's statement, not an independent timestamp. An anchor whose `anchoredAt` is more than 10 minutes ahead of the verifier's clock is not used (it counts as no anchor). Within one origin, an anchor of a larger size MUST NOT have a smaller `anchoredAt`.
- `prev` is the size of the anchor before this one in the same generation; the first anchor of a generation has none. The chain lets the mirror recover every anchor it missed, and a broken chain is a failure.
- There is one anchor per (origin, size). Two anchor files of one origin and size with different notes are a failure; checkpoints are compared by origin, size and root, never by file bytes.

Anchors are trusted only together with the mirror's history (§12).

## 9. `index.json`: rewind records

```json
{"records":[{"kind":"rewind","note":"<signed note>"}]}
```

Each record is a signed note under the log key (key name `log_name`). A rewind note's text, one field per line:

```text
emojery-rewind-v1
log.emojery.app/g1          origin: the generation it opens
log.emojery.app/g0          forkedFrom: the generation it closes
1790000000000               at: Unix milliseconds of the stop
1048576                     N: size of the shared prefix
<rootN, base64>
1050108                     M: size of the last published checkpoint of the closed generation
<rootM, base64>
database incident           reason: one line of UTF-8
```

- The current origin is the `origin` of the last rewind record, or `<log_name>/g0` without records. Unsigned fields are never trusted.
- Records form one chain, in file order: the first forks from `<log_name>/g0`, each next one from the `origin` of the one before, and each `origin` is `<log_name>/g<k+1>` where `g<k>` is its `forkedFrom`. A note is exactly the nine lines above. A record that breaks the chain, a second record forking the same generation, and a record of unknown kind are failures. A rewind note verifies under the log key that covers size `N`.
- `N ≤ M`. The closed generation's tree at `N` MUST have root `rootN`, and its tree at `M` root `rootM`: an RFC 6962 consistency proof from (`N`, `rootN`) to (`M`, `rootM`) over the closed generation's tiles shows both. Every checkpoint and anchor of the closed generation of size at most `N` MUST be consistent with (`N`, `rootN`), and every one of size at least `N` with (`M`, `rootM`). The new generation's tree at `N` MUST also have root `rootN`. So the new generation starts from the closed one's exact prefix: a rewind can drop leaves, never rewrite them.
- The mirror (§12.2) keeps `index.json` append-only. The bucket's records MUST begin with every record the mirror holds; a record the mirror has and the bucket does not is a failure (a rewind hidden from some readers).
- REACT leaves below `N` are verified with the origin of the generation they were sealed in; a REACT at or above `N` signed for the closed origin is invalid.
- `M` MUST be at least the largest closed-generation size the verifier knows of (its saved state, the closed generation's last anchor in the mirror). A smaller `M` is a failure.
- Leaves `[N, M)` do not carry over. The verifier reports every closed generation, the number of dropped leaves and how many of them were anchored.

## 10. Provider keys

`g<k>/jwks/<provider>/<hex modulus_hash>.json` and the mirror's `jwks/<provider>/<hex modulus_hash>.json` hold one RSA key as canonical JSON: `{"e":"<base64url>","kty":"RSA","n":"<base64url>"}`, keys in this order, no whitespace, no trailing newline. `n` is the modulus without leading zero bytes; `sha256` of its bytes is the file name and the ENROLL `modulus_hash`.

The provider of an ENROLL is the one §11 maps its (`iss`, `aud`) to; every witness is about that provider only. A modulus is **witnessed** when it is in the mirror's `jwks/<provider>/` and the file's sha256 appears in the `jwksAdded` list of a line of the mirror's `verdicts/`, in an Internet Archive snapshot of the provider's pinned JWKS address, or in the provider's live JWKS at that address. A modulus present only in the publisher's `g<k>/jwks/` is unwitnessed: a `WARN` while the first anchor covering the ENROLL is younger than 7 days by `anchoredAt`, a failure after that. A modulus absent everywhere is a failure.

## 11. Trust anchors

A verifier carries, in its own code and per `log_name`: the log's public key (with the size range each key covers), the verification key hash of each ENROLL version, `salt_commitment`, the accepted (`iss`, `aud`) pairs with each provider's JWKS address, and the keys of the Rekor shards with their periods. None of these is read from a file the operator publishes. An ENROLL whose (`iss`, `aud`) is not listed for the log is invalid; the staging test issuer is listed only for `log-staging.emojery.app`. A log lists exactly one `aud` per `iss`: the nullifier hashes `aud`, so a second client id would give one provider account a second nullifier and a second vote.

## 12. Verification rules

### 12.1 The fold

Counts are not stored in the log; they are computed from it. A verifier walks the leaves in `seq` order and keeps, per **pair** (nullifier × site × target_id), the current reaction and the last counter.

| Leaf | Valid when | Effect |
| --- | --- | --- |
| ENROLL | the proof `g<k>/proofs/<seq>` hashes to `proof_hash` and verifies (§4.3); `proof_hash` has not appeared in an earlier ENROLL; the modulus is witnessed (§10); (`iss`, `aud`) is listed (§11) | registers the device key under `nullifier` |
| REACT | `enroll_seq` is an earlier ENROLL, not retired; the signature verifies under that ENROLL's key and `enroll_hash`, with the origin of the generation the REACT is sealed in; `prev_reaction` equals the pair's reaction; `counter` is greater than the pair's counter | the pair's reaction becomes `reaction`; −1 for the old reaction, +1 for the new |
| REVOKE | `enroll_seq` is an earlier ENROLL (retired or not) | every non-empty pair of its nullifier becomes empty (−1 each); counters carry on; ENROLLs stay usable |
| RETIRE | `enroll_seq` is an earlier ENROLL whose nullifier equals the leaf's; `self`: the signature verifies under that ENROLL's key and `enroll_hash`, and that ENROLL is not retired; `request`/`legal`: `sig` empty, `case_id` 16 bytes | every non-empty pair of the nullifier becomes empty (−1 each); the pairs' counters start over; every ENROLL of the nullifier sealed before this leaf is retired |

- A pair the fold has no state for has an empty reaction and counter 0, so its first REACT has a counter of at least 1. After a RETIRE the fold has no state for any pair of the nullifier, whatever the pairs held before. A REACT whose `reaction` equals its `prev_reaction` is valid and changes only the counter.
- A retired ENROLL cannot carry a REACT: deleting an account kills its old signatures, so they cannot be replayed onto the emptied pairs. Binding the signature to `enroll_hash` does not replace this rule.
- A new ENROLL of the same nullifier after RETIRE starts a fresh registration; the same device key may enroll again with a new proof. "Earlier" for `proof_hash` means earlier in the current tree: leaves a rewind dropped do not count.
- A REVOKE or RETIRE with no non-empty pairs is valid.
- Any invalid leaf is a failure of the whole log.

**Counts of a target** are the number of pairs per reaction. The top 10 is ordered by count descending, then by reaction bytes ascending (a bytewise comparison, never a UTF-16 one); `total` is the sum over all reactions.

### 12.2 Checkpoints and anchors

- Only an anchored checkpoint is trusted: its note verifies, `anchorSig` and `entry` match it (§8), the inclusion proof holds under a pinned shard key, and the anchor agrees with the mirror's history of anchors. A newer checkpoint is checked for consistency and reported as not yet anchored.
- The mirror (`emojery-tlog`) commits every anchor append-only, under the same `g<k>/anchors/` paths as the bucket. For an anchor of size `s` and the mirror's `g<k>/anchors/latest.json` of size `L`: the mirror's `g<k>/anchors/<s>.json` is present with the same root, or `L < s` and the anchor is consistent with the mirror's latest — normal. The mirror's `<s>.json` with another root, an anchor inconsistent with the mirror's latest, or no `<s>.json` while `L > s` and anchor `L` is at least two anchor intervals newer — failure. Files named `<size>.conflict-<sha256>.json` are evidence, shown and never used.
- An anchor the mirror has not seen is trusted only for a while: when the mirror cannot be read, or its latest anchor is more than four anchor intervals older (by `anchoredAt`) than the bucket's, the verdict is `WAIT`.
- Within one origin, every checkpoint and anchor MUST be consistent with every other the verifier has seen. Across origins, §9 decides.

### 12.3 Verdicts

- `PASS` (exit 0): everything up to the last anchor holds and the tail after it is consistent. Notes (`WARN`) ride along: a mirror a little behind, an unwitnessed provider key younger than 7 days, a source that did not answer, leaves dropped by a rewind.
- `WAIT` (exit 3): published leaves have gone without an anchor for more than two anchor intervals, by the time the verifier first saw them (its state) — anchors in unpinned shards and future-dated anchors count as none; or the mirror is unreadable or more than four anchor intervals behind; or the newest anchor is of a kind the verifier does not know.
- `FAIL` (exit 1): a contradiction in data that was read — a signature, a root, inconsistent checkpoints, an invalid leaf, a count that differs from the fold, content against an anchor.
- An unreadable source is never a failure. The one exception: an object below an anchored checkpoint that the host does not serve while it serves its neighbours, when the first anchor covering the object is older than 7 days by `anchoredAt`, is a failure ("data withheld").

## 13. Counts

`GET https://api.emojery.app/v2/counts/<site>/<base64url(target_id)>.json` answers `{"counts":{"<reaction>":<n>,...},"total":<n>}` with the top 10, and the headers `X-Emojery-Published-Size` and `X-Emojery-Published-Origin`: the published log size and origin the numbers belong to. The path segment is the base64url of the UTF-8 `target_id`, without padding. A verifier compares the answer with its fold at that same origin and size. An answer at a size beyond the verifier's checkpoint means a stale checkpoint: the verifier rereads it, and an answer still beyond the checkpoint it rereads one anchor interval later is a failure.

## 14. Other signed messages

These never enter the log; they are listed so every Ed25519 tag of the protocol is in one place.

| Message | Bytes |

Every message a device key signs starts with an `lp16` domain tag, so no tag is a prefix of another. The log key signs only signed-note text (checkpoints, rewind records) with Ed25519 and anchored notes with Ed25519ph; a note parses only as the exact line structure of §7 or §9.
